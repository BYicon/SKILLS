# 成熟产品界面的 UI、UX 与工程

从三个层面交付完整的产品界面：UI 建立独特但克制的视觉语言，UX 顺应真实工作习惯并降低操作成本，工程通过设计系统保证一致、稳定和可维护。
默认以成熟团队持续维护的产品为完成度参照：版式经过整体设计，真实内容得到恰当呈现，组件与状态属于同一套语言，细节经过实际画面的修正。功能控件齐全、排列整齐和统一配色，只能证明结构已建立。
这个标准适用于工具、内容、营销和后台页面，不预设 C 端风格或极简方向。克制体现为明确的主次与有用途的细节；视觉丰富度来自内容和一致的设计语言，不靠增加无关装饰或模块。

## 任务边界

- 遵守项目 `AGENTS.md`、平台要求和既有设计系统；有明确设计稿时优先保真还原。用户只要求评审时不修改文件。
- 新建页面或整体改造，执行完整的设计、实现和验证流程；局部修改只处理相关区域与受影响行为，不扩展为整页重构。
- 保留业务规则、接口、路由、权限和已有能力。不伪造数据、评价、处理进度、结果或产品承诺；演示数据和未接入能力必须明确标注。

## 先建立依据与验收目标

实现前读取目标页面、相关组件、设计变量、图标和图片资源，以及项目已有的启动和检查命令。识别当前环境可用的预览、截图与交互工具，提前确定如何验证，避免写完代码才发现没有验证路径。

明确用户是谁、使用频率、核心任务和已有操作习惯；改造时先尝试运行并查看当前页面。检查用户必须输入、判断、等待和来回切换的位置，区分真实问题与源码推测。

页面级设计先确定完成度参照，按用户提供的设计 → 项目中成熟的同类页面 → 适合平台的真实产品选择，并实际查看可访问的画面。比较相近的任务、内容密度与交互复杂度，提取主体比例、排版节奏、内容呈现和组件关系；不要照搬无关业务结构或拼接不协调的风格。

简要说明当前页面与参照之间的具体差距，以及准备落实的视觉关系。例如“现有列表的筛选、表格和分页像三个独立示例；沿用项目数据页的公共边界、密度与工具栏层级”。局部修改沿用已有设计，不额外启动整页调研。缺少可访问参考时，自主明确设计依据并推进，如实说明依据范围。

页面级任务在编码前简要确定三件事，局部任务只确定受影响的部分：

- **UI**：完成度参照、视觉中心、区域比例、信息密度，以及需要落实的内容呈现和组件关系。
- **UX**：核心任务从入口到结果的操作路径、需要保留的上下文，以及相关失败与恢复方式。
- **工程**：复用哪些设计变量与组件，哪些状态和业务能力已有实现，确实缺少什么。

决策要能指导实现，例如“预览占首屏主要空间；常用设置紧邻预览；高级设置按需展开且保留输入；底部制作按钮复用公共提交组件”。“现代、简约、高级”不足以作为实现依据。缺失信息会实质改变业务规则时再询问，不让用户逐项决定日常审美选择。

## UI：达到成熟产品的视觉完成度

### 先完成整屏设计

- 从真实产品对象、品牌和使用场景形成辨识度，例如作品的呈现比例、业务数据的编排或编辑区与预览的关系；不要让所有页面都套大标题、三列卡片和底部行动区。
- 让主要内容获得足够空间，保留有用的导航、预览、分组、帮助与状态。不能以减少元素数量作为优化成果，也不能把有价值的品牌表达全部清掉。
- 在首屏与完整页面两个尺度上安排主体、局部密度和留白，检查区域比例、内容边界与视觉重心。大段留白、全宽容器或紧凑布局都应有适合内容的构图理由，不能仅按功能清单逐块摆放。
- 将上传、无数据、未选择等空态作为正式页面设计，明确内容锚点、入口和辅助信息的主次；有内容后让预览、列表或数据自然成为主体。两种状态分别检查，不能把功能占位区域直接当成完整的视觉方案。

| 页面任务 | 优先组织的关系 |
| --- | --- |
| 图片、视频、创作工具 | 预览与编辑相邻，控制区不挤压作品，提交、进度和成果位置清晰。 |
| 作品、商品、内容列表 | 图片比例与文字节奏一致，信息便于比较，筛选和数量属于列表上下文。 |
| 业务后台 | 筛选、表格、批量操作形成连续工作区，列宽、数字与操作对齐。 |
| 品牌、营销页面 | 标题、真实产品画面与行动入口共同构成首屏，后续内容围绕具体卖点展开。 |

### 用一致的细节完成画面

- 建立内容边界、主轴与连续的对齐关系。通过间距级差表达字段内部、同组控件和不同任务区域的关系；边缘错位需要明确的构图理由。
- 明确页面标题、分组、正文、辅助信息与关键数字的层级，结合字号、字重、位置和明暗区分主次。辅助信息仍须可读；用实际中文长文本检查断行、行高与截断。
- 按关系选用间距、底色、分隔线或卡片。检查边界是否重复，避免每组控件都套装饰性卡片；也不要为减少卡片破坏必要分组。
- 让颜色分别承担品牌、动作和状态的角色。圆角、边框与阴影服从组件角色和设计变量；渐变、材质和插画只在支持视觉方向时使用。
- 优先使用真实资源，检查清晰度、裁切与比例。大面积占位框不能代表完成后的设计，不能靠虚构评价、统计或宣传填充页面。
- 字体服从品牌、中文可读性和平台能力；图标统一来源、线宽和视觉尺寸。默认不用 Emoji 充当功能图标，用户内容或表情产品本身的 Emoji 可以保留。

结构实现后，结合实际渲染完成视觉打磨，具体调整区域比例、排版层级、组件密度、色面关系和资源呈现。标准表单、原生控件和简约布局都可以是成品方案，判断依据是它们是否与内容和整页设计协调；不强制增加图片、卡片、动效或其他装饰。

## UX：顺应真实工作习惯并降低操作成本

### 把核心任务走通

- 按用户的任务顺序组织输入、操作与结果，常用操作易于发现，次要和高级操作按需呈现。工具页与后台优先支持连续工作，不先要求用户阅读大段产品介绍。
- 利用已有信息和明确的业务默认值减少重复填写、重复确认与页面往返。筛选、切换、返回或失败重试时，按任务需要保留输入、选择与位置；不要为了视觉整齐增加步骤。
- 让必要的格式、费用、限制、权限和风险出现在影响决策的位置。按钮写清动作与对象，帮助用于消除实际疑问，删除泛泛宣传和重复说明。
- 核心按钮、导航、筛选和编辑必须有真实行为。操作结束后，用户能找到结果并继续下一步；未接入的能力明确说明，不能用成功提示替代实际处理。

### 处理相关复杂场景

- 对本次路径明确触发、等待、结果和恢复：无内容时知道怎么开始，无搜索结果时能调整条件；提交时有反馈并防止重复提交；失败时保留有效输入、定位原因并提供可行的恢复操作。
- 对已有批量操作、长任务或多步骤流程，处理相关的部分失败、取消、返回和重新进入场景。只覆盖真实需求与现有能力，不凭空增加业务流程或承诺取消、恢复能力。
- 弹窗和抽屉按平台惯例处理打开、关闭、焦点进入与返回；列表和状态变化避免无故跳位。动效解释反馈与空间关系，并遵循减少动画的设置。
- 使用语义正确的控件、可见标签与焦点、可访问名称和有效错误提示。点击区域、键盘操作、触摸、输入法遮挡、安全区与滚动都围绕实际操作检查；固定栏应为内容和焦点留出位置。
- 移动端按任务优先级重排内容，避免仅把桌面多列堆成长页；关键操作不能只在悬停时出现。

## 工程：让设计系统约束实现

- 先查找并复用项目已有的颜色、字体、间距、尺寸、圆角和层级变量，以及按钮、字段、表格、弹窗等组件。相同语义与状态在不同页面保持一致，不逐页自由生成一套样式。
- 设计系统缺少能力时，在任务范围内补充最小的语义变量、组件变体或公共能力；局部调整优先使用现有扩展方式，不用零散硬编码或样式覆盖制造同类组件的差异，也不顺手重建整套组件库。
- 组件职责、数据请求与界面状态遵循项目结构。对确有复用价值的内容抽取公共实现，避免复制整段页面；一次性且强耦合的细节不为抽象而拆分。
- 让加载、成功、失败、禁用和选中状态来自真实状态模型。涉及异步筛选、快速切换或重复操作时，处理相关竞态与状态清理，避免旧结果覆盖新选择、失败后仍显示成功或界面卡死。
- 沿用现有技术栈与依赖，不为单个视觉效果引入整套库。修改公共组件或变量时检查相关使用处，避免修好当前页却破坏其他页面。

## 验证：分别检查 UI、UX 与工程

页面实现必须尝试使用项目已有的运行方式和当前可用工具验证。具备运行与查看能力时，必须实际查看画面并操作，不能只做编译或阅读源码就交付 UI 验收结论。仅评审时检查可访问页面或提供的截图，不执行实现步骤。

### UI：打开并查看实际画面

- 打开受影响的页面，检查目标平台的实际渲染并查看截图。DOM、样式数值和构建成功不能代替看画面；小程序使用其开发者工具、目标平台预览或对应截图，不能用 H5 冒充验收。
- 页面级响应式任务检查项目支持的桌面和窄屏尺寸；仅移动端任务至少检查一个目标窄屏。局部任务检查受影响区域与相关尺寸，不默认执行全平台验收。
- 使用真实内容或明确标注的代表性测试内容，检查相关的正常、长文本、空、加载与错误画面，避免只看理想占位数据。
- 改造任务尽量以相同尺寸对照修改前后画面，并与选定的完成度参照比较。不能只以没有溢出、元素对齐或颜色统一判定视觉验收通过，还需检查以下关系：

| 检查面向 | 实际画面中的验收依据 |
| --- | --- |
| 整屏构图 | 主体尺寸符合任务，区域比例与视觉重心协调；内容边距、疏密和留白有连续的组织关系。 |
| 内容呈现 | 实际作品、数据或文字得到完整呈现；空态也有明确层级，示例与占位内容没有掩盖真实内容的问题。 |
| 视觉系统 | 标题、正文、辅助信息与动作层级可辨；组件、色面与状态在当前页和相关页面之间保持一致。 |
| 完成细节 | 基线、图标、边界、裁切、长文本和对比度经过检查，各相关尺寸下没有已知的主要视觉问题。 |

记录实际发现的问题和对应修正，例如“下半屏留白与上部密集控件失衡，重新分配内容间距并调整主区域比例”。修正后重新查看受影响画面；不能只报告“已截图检查”，也不为凑轮次做无依据的改动。

### UX：实际走通相关操作

- 在任务授权范围内验证从入口、输入、提交到结果的核心路径，并检查本次涉及的失败恢复、取消或返回。不能只点击主按钮看到提示就认为流程可用。
- 检查操作反馈、输入与选择保留、重复操作和结果可达性；涉及弹窗、滚动或移动输入时，检查焦点、遮挡和关闭后的上下文。修复发现的问题后重走受影响路径。

### 工程：检查实现与回归

- 遵守项目必需检查，并按变更影响运行已有构建、类型检查、测试或静态检查。修改公共组件时验证相关使用处，确认设计变量、交互状态和业务行为保持一致。
- 不为文案或单个样式调整添加仅匹配实现文字的测试；涉及状态流转或公共行为时，优先使用已有测试验证有意义的行为。

无法运行、查看或操作时，记录实际尝试、具体阻塞点和未验证范围，继续完成可执行的检查。不得虚构截图、操作记录或通过结论，也不能将“代码已完成”表述为“UI 与 UX 已验收”。

## 交付

实现任务交付实际代码，简要说明 UI、UX 与工程的主要变化。列出实际查看的页面与尺寸、走过的关键操作和运行过的检查；有截图时给出可访问的位置，并说明尚存问题和未验证范围。

评审任务按影响排序给出位置、依据和修改建议，区分实际观察与代码推测。不要输出长篇设计自评、审美分数或效果保证；完成度以可见结果、可用流程与一致实现接受检验。
