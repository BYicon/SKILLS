# AGENTS.md Optimizer

## 目标与边界

优化现有 Codex 指令体系，使规则**易发现、少重复、范围准确、行为明确、结果可验证**。以当前仓库的真实情况为准，不套用空泛模板。

- 仅在用户要求优化时修改规则；用户只要求审查时保持只读。
- 优先最小必要改动；保留业务、安全、权限、架构、兼容性等重要约束。
- 只修改用户授权范围内的 `AGENTS.md`、`AGENTS.override.md` 和确有必要的配套规范文档。
- 不修改业务代码、依赖、CI、Git 配置或用户级规则；未经明确授权不提交、不推送。
- 遇到规则冲突、关键规则含义不明或可能削弱安全边界时，保留原规则并报告，不擅自删除。

## 执行流程

### 1. 发现与定位

1. 确认当前工作目录与仓库根目录（如可用，执行 `pwd`、`git rev-parse --show-toplevel`）。
2. 如需核对全局影响或发现配置，只读查看相关用户级规则与配置，确认实际 `CODEX_HOME`、`project_doc_fallback_filenames` 和 `project_doc_max_bytes`。不得修改这些全局文件，除非用户明确授权。
3. 在当前任务适用范围内查找 `AGENTS.md`、`AGENTS.override.md` 和已配置的替代文件名。不要漏掉被 `.gitignore`、`.git/info/exclude` 等忽略的规则文件；相关父目录按路径定点检查，不递归扫描仓库外目录。
4. 根据下述发现规则，整理文件作用范围与候选加载链；区分找到的文件、按规则应选中的文件和实际确认已加载的文件。
5. 阅读项目 `README`、技术栈文件、构建与测试脚本、现有规范目录等必要事实材料；不要递归阅读所有项目文件。

在目标仓库根目录，可用精确文件名筛选查找规则文件；配置了替代文件名时，追加相应的 `-g`：

```sh
rg --files --hidden --no-ignore \
  -g 'AGENTS.md' -g 'AGENTS.override.md' \
  -g '!**/.git/**' -g '!**/node_modules/**' -g '!**/dist/**'
```

核对指令发现与覆盖规则（来源：[OpenAI 官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)；行为有差异时结合当前版本与配置确认）：

- 全局：在实际 `CODEX_HOME` 中依次检查 `AGENTS.override.md`、`AGENTS.md`，采用首个非空文件。
- 项目：从项目根目录到当前工作目录逐层检查；没有项目根目录时只检查当前目录。每层按 `AGENTS.override.md`、`AGENTS.md`、已配置替代文件名的顺序选首个非空文件，每层最多一个。
- 合并：从外到内拼接，较深层的冲突规则优先；其他子目录中找到的文件不因此成为当前启动的加载来源。
- 截断：检查候选加载链的合计字节数与 `project_doc_max_bytes`，识别可能未完整载入的内容；不要把文件存在当作已完整生效的证据。

### 2. 审计问题

按重要程度找出：

- 冲突：同一范围内规则矛盾，或与上级/下级指令及现有项目约定冲突。
- 失效：路径不存在、命令不可执行、组件或技术栈已过时。
- 过度：重复表述、无操作价值的口号、每次任务都执行全套流程、每步全量测试、无变化仍重复核验，以及无实际需求或风险依据的防御与兜底要求。
- 模糊：只有“高质量”“严格遵守”“有高级感”等无法判断的要求。
- 错位：只针对局部模块的长规则放在全局或根目录，或应由工具强制的规则仅停留在提示词。
- 缺失：缺少对相关文档的触发条件、重要修改边界、必要验证及诚实交付要求。

记录支持问题的具体文件与原文位置；区分已验证事实、推断和建议。

### 3. 设计优化方案

将内容归入适当层级：

- 根 `AGENTS.md`：项目简介、不可忽略的边界、关键命令、相关文档入口、简短的工作与交付要求。
- 子目录 `AGENTS.md`：真正只适用于该模块、且与项目通用规则不同的约束。
- `docs/`：较长的 UI/UX、前端、API、测试、部署等专项知识与规范。
- 自动化工具：Lint、类型检查、测试、架构校验、CI 等可确定性验证的要求（只建议，不在本次擅自实现）。

`docs/` 中的普通文档**不等于自动加载的指令**。在 `AGENTS.md` 中提供精确路径和读取条件，如“涉及 UI/交互修改时，先阅读 `docs/DESIGN.md`”；只为项目中真实存在的文档建立引用。

原则：按需读取，不强制每个任务阅读全部规范；简单改动轻量验证，复杂/高风险改动增加必要检查。不要为分层而过度创建文件。

#### 实现与验证的投入边界

以下原则也适用于本 skill 的执行。审查项目规则时据此取舍，不默认向每个项目追加通用编码规范：

- **需求优先**：让主要精力用于完成当前明确需求。收窄或删除仅为假想场景要求的兜底、兼容、重试、预防性抽象或顺手重构；保留外部输入校验、鉴权、数据一致性保护和真实失败处理。
- **操作适量**：目标、范围和相关状态未变时，沿用已确认的结论，不要求每一步重复确认或检查完整性；保留权限、安全边界及破坏性操作前的必要核对。
- **验证匹配影响**：选择覆盖本次行为的最小充分检查，在相关改动完成后集中执行；低风险改动不默认新增测试，也不要求每小步运行全量测试、构建或 E2E。项目明确要求的检查仍须完成。
- **有停止条件**：检查通过且相关问题已解决后，继续交付；只有新变化影响已有结论、检查失败或仍有未覆盖风险时，才重跑相关检查或扩大验证，并说明原因。不用“再保险”作为重复检查的依据。

### 4. 实施（仅限用户要求修改时）

1. 保留原有明确且有价值的规则；只删除或合并被证实冗余、过时且不影响约束的内容。
2. 使用项目真实的目录、组件、技术栈和脚本名称；无法证实的内容不编造。
3. 把模糊表述改成可执行要求，优先描述**何时适用、应该做什么、如何验证**。
4. 对必须人工判断的质量要求，明确检查对象与人工验收边界，不声称已可完全自动验证。
5. 如存在用户未提交的变更，尊重已有工作，不覆盖或回退无关内容。
6. 没有明确必要时不要新增规范文件；如果新增，确保从适用的 `AGENTS.md` 可以按需定位。

可参考的紧凑根文件结构（按需保留章节，不机械照抄）：

```md
# Project Guidelines
## Project Context
## Core Constraints
## Documentation Routing
## Development & Verification
## Delivery
```

### 5. 验证

- 核实每个新增引用的相对路径真实存在，读取条件与适用范围一致。
- 检查覆盖、重复、冲突与安全约束是否仍正确。
- 排查“不生效”或修改了加载层级时，在目标工作目录的新运行/新会话中核对指令来源与关键约束。Codex 启动时构建加载链；不要用当前旧会话证明修改已生效。未实际核验时，明确说明仅完成静态检查，列出待确认项。
- 用 `git status --short` 与 `git diff --check`、`git diff -- <相关文件>` 检查修改；新建且未跟踪的文件也要逐个检查内容。
- 如项目有现成的 Markdown/Lint 检查器，可运行与本次文档变更直接相关的检查。
- 文档优化通常**不需要**运行应用的完整测试、构建或 E2E 测试。
- 对没有真实执行的测试，明确写“未执行”，不要声称通过。

### 6. 交付

简洁汇报：

1. **范围**：实际检查、修改、新增的文件。
2. **发现**：主要冲突、冗余、失效引用或规则错位（引用具体路径）。
3. **改动**：合并/删除/保留的关键规则，以及按需读取的文档映射。
4. **验证证据**：实际运行的检查和结果、是否仅有预期文件被修改。
5. **风险**：不能确认或需要人工决定的规则。

如果没有发现值得修改的地方，说明“无需修改”，不要为了产生 diff 而重写。

## 触发边界

**适用请求**：

- “优化项目的 AGENTS.md”
- “检查 AGENTS.md 为什么不生效”
- “把项目规则拆到 docs 并配置按需读取”
- “审查多个 AGENTS.md 是否冲突、重复或过长”

**不适用请求**：

- 建立或系统重建项目概览、架构、领域知识等 AI 首读文档体系；如环境提供 `project-context-bootstrap`，该类请求由其处理，本 skill 不要求安装或联动它。
- 普通页面开发、修 Bug、代码审查、安装依赖、部署任务。
- 单纯询问 Agent 原理，且不要求审查或修改当前仓库规则。
