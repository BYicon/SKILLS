# 文档模板

把下面的结构当作起点，再用从代码里核实到的仓库事实替换占位内容。

## `docs/PROJECT_CONTEXT.md`

建议章节：

- 文档目的
- 一页摘要
- 仓库结构
- 先看哪些代码
- 系统主链路
- 业务能力边界
- 当前技术决策
- 当前页面/服务与能力映射
- 运行与部署
- 最近工作重点
- 必须记住的仓库约束
- 什么时候必须回到源码
- 维护规则

规则：

- 让它成为首读主入口
- 优先按任务入口组织，不要写成目录清单
- 明确标注占位模块或脚手架区域
- 总长度应短于所有专题文档长度之和

## `docs/ARCHITECTURE.md`

建议章节：

- 架构总览
- 分层设计
- 核心模块图或数据流图
- 主业务链路
- 前端/后端/基础设施分工
- 数据与存储
- 共享包现状
- 运行环境策略
- 当前架构风险与注意点

规则：

- 解释边界和职责，不要罗列每个文件
- 明确跨模块依赖和高耦合区域

## `docs/DOMAIN.md`

建议章节：

- 领域总述
- 核心业务对象
- 关键状态流转
- 数据库存储映射
- API 协议约束
- 前端页面如何映射领域对象
- 最容易误解的业务点

规则：

- 重点写清对象、生命周期、归属关系和不变量
- 如果“存储模型”和“界面投影”不同，要明确分开描述

## `docs/CONVENTIONS.md`

建议章节：

- 代码归属
- 包与构建约定
- 跨端契约
- 组件/框架约定
- 数据兼容策略
- 注释约定
- 代码生成与重构约定
- 文档更新规则
- 当前仓库的落点建议

规则：

- 这里只放长期有效的规则，不写短期项目状态
- 如果规则是全仓库硬约束，要同步体现在 `AGENTS.md`
- 如果用户提供通用代码约束，优先吸收其中真正长期有效且与仓库现状不冲突的部分

## `docs/CHANGELOG_FOR_AI.md`

只记录会改变后续接手成本的变更，例如：

- 新增核心模块
- 重大架构调整
- 契约或数据结构变化
- 部署或环境策略变化
- 占位区域转为真实业务
- 入口文件策略变化，例如 `AGENTS.md`、`CLAUDE.md`、文档索引调整

不要记录常规样式修改或对后续接手成本没有影响的局部重构。

## `AGENTS.md`

用途：

- 仓库级硬约束
- 必须遵守的阅读顺序
- 后续会话在编码前必须执行的规则
- 用户明确要求的代理执行约束，例如“提供绝对路径时直接使用，不再检索”

避免：

- 重复写长篇架构说明
- 重复 `docs/PROJECT_CONTEXT.md` 已经覆盖的项目概览

## `CLAUDE.md`

推荐最终形态：

- 如果它只是兼容层，就收缩成一个很薄的入口文件
- 明确指向 `AGENTS.md`
- 不要重复叙述同一套阅读顺序

最小形态：

```md
# CLAUDE.md

请先阅读 `AGENTS.md`。
```
